# modules/change-management.md · 变更管理

> **目标**：比赛中改模型/方法/数据时，知道会连锁影响什么，别改一处崩三处。72 小时里必改，关键是改得可控。

## 1. 为什么要管变更

比赛中"换模型""改假设""换数据"是家常便饭。不改记录的后果：摘要还是旧数字、验证没重跑、附录代码与正文不符。

## 2. 版本控制

- **建议用 git**（仓库已 init）：每完成一个可跑的节点就 commit，写清"改了什么/为什么"。
- 没有 git 时：用版本目录 `v1_baseline/ v2_main/ v3_improved/`，不直接覆盖上一版结果。
- 原始数据永远只读，另存处理后副本。

## 3. 变更影响评估（改之前先想）

每改一处，问四个连锁：

| 改了什么 | 连锁影响 |
|---|---|
| 换模型 | 结果数字变 → 摘要/正文/附录全要更新；验证要重跑；创新点表述可能变 |
| 改假设 | 模型推导要重推；灵敏度分析可能要重做 |
| 换数据/预处理 | 所有结果重跑；对比基线要在同数据上重算 |
| 改目标函数 | 优化结果全变；图表重出 |
| 改 Figure 总数 | visual plan 退回 draft；补/删独立证据；重报逐图清单、预计页数区间并请用户重新锁定 |
| 改论文总页数 | 先核对证据容量与官方限制；更新用户裁决记录，不以版式膨胀或删关键证据硬贴目标 |

## 4. 记录规范

每次变更记一行：

- 时间 / 改了什么 / 为什么改 / 影响了哪些章节 / 哪些验证要重跑。
- 策略选择另记：小问 / A、B 证据路径 / 推荐及理由 / 用户选择 / 回退版本。用户未选择前不覆盖当前主路线。
- Figure 数量另记：原建议数 / 用户锁定数 / 新增或删除的 Figure ID 与证据 / 对实验和预计页数的影响 / 新确认记录。未重新确认前不生成变更后的正式图。
- 篇幅另记：锁定 Figure 数 / 证据支撑区间 / 用户选择的具体页数或“证据充分即可” / 后续变更原因。

## 5. 回退预案

- 改崩了能一键回到上一个可跑版本（git 或版本目录）。
- D3 之后**冻结主版本**：只改文字和格式，不再动模型和结果，避免临交前数字又变。
- 重大改动（换主模型）只允许在 D2 中午前；之后只做小修。

### 5.1 终稿重跑的缓存与派生产物

“冻结主版本”不等于继续相信旧缓存。终稿重跑是在**不改方法合同**的前提下验证整条依赖链：

- 先列出原始输入、处理后数据、模型缓存、结果表、Figure、TeX 输入和交付包的依赖顺序；原始输入只读并记录校验值。
- 模型派生缓存与旧交付件移入带时间戳的备份目录，确保可恢复；不得直接覆盖后才发现新链路失败。
- 仅删除或移出可由源码再生的派生物；路径含义不清、目标范围过大或可能包含人工结果时先停下核对。
- 全量重跑后，把关键指标、拆分、随机配置、模型参数和 Bootstrap/消融/归因结果与冻结版逐项对账。文本换行或 JSON 末尾换行可记录为非语义差异；数值、样本数、模型配置或图中证据变化必须解释。
- 图表生成目录与 LaTeX 读取目录分离时，显式同步并按哈希核对；“生成成功但论文仍引用旧图”视为失败。
- 只有新链路、干净编译和全部交付副本都通过，才原子替换旧件；否则回退备份并保留失败日志。

## 6. 常见错误

- 改了模型忘了改摘要。
- 重跑结果后没更新附录。
- 没有版本备份，改崩了找不回上一版。
- D3 深夜还在换模型，结果来不及验证就交。
- 重跑脚本却保留自动复用缓存，最终 PDF 实际仍混入旧结果。
- 只覆盖根目录 PDF，没有同步源码包、复现包、页数说明和校验清单。
